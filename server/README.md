# Сервер GRAFF

Боевой сервер приложения кафе GRAFF (Чири-Юрт). Отвечает за три вещи:

1. **Вход гостя по SMS** — номер телефона, код из SMS, токен на 90 дней. Пароля нет.
2. **Заказы** — приём, расчёт суммы, нумерация, занятость столиков, хранение истории.
3. **Живые статусы** — кухня меняет статус, телефон гостя узнаёт об этом сразу
   (Server-Sent Events, без перезагрузки экрана).

Технически: Node 22, Fastify 5, SQLite (`better-sqlite3`). TypeScript выполняется Node
напрямую (`--experimental-strip-types`), сборки сервера нет. Внешних сервисов, кроме
оператора SMS, не требуется — всё живёт на одной виртуальной машине в России.

## Из чего состоит

| Файл | Что внутри |
| --- | --- |
| `src/server.ts` | точка входа: Fastify, CORS, ограничение частоты, `/health`, завершение работы |
| `src/config.ts` | все настройки из переменных окружения |
| `src/types.ts` | контракт API, общий с приложением (`src/lib/api.ts`) |
| `src/db.ts` | SQLite: таблицы, репозитории, журнал `audit` |
| `src/auth.ts` | токены (HS256), хэш PIN (scrypt), хэш кода (HMAC), нормализация телефона |
| `src/sms.ts` | отправка кода через sms.ru или smsc.ru |
| `src/events.ts` | подписчики SSE и рассылка событий |
| `src/routes/*.ts` | маршруты: вход, заказы, панель персонала, поток событий |
| `scripts/add-staff.ts` | завести сотрудника кухни |
| `scripts/smoke-test.ts` | сквозная проверка сервера (только на тестовом стенде) |
| `data/graff.db` | база: гости, коды, заказы, столики, сотрудники, журнал |

## Маршруты

Приложение собирается с `VITE_API_URL=/api`, поэтому обращается к адресам с префиксом
`/api`. Сам сервер отдаёт маршруты **в корне** — префикс срезает nginx
(`proxy_pass http://graff_app/;` в `deploy/nginx.conf`). В таблице — путь так,
как его видит приложение; на сервере это тот же путь без `/api`.

| Метод | Путь | Кто | Что делает |
| --- | --- | --- | --- |
| `POST` | `/api/auth/request-code` | гость | Отправляет код в SMS. Без `consent: true` отказывает. Не чаще 1 SMS в минуту и 5 в час на номер |
| `POST` | `/api/auth/verify` | гость | Меняет код на токен клиента (`TOKEN_DAYS`), создаёт или обновляет профиль |
| `GET` | `/api/me` | клиент | Профиль: имя, телефон, согласие на рекламу |
| `PATCH` | `/api/me` | клиент | Уточнение данных: имя, согласие на рекламу |
| `DELETE` | `/api/me` | клиент | Удаление аккаунта и отзыв согласия; заказы обезличиваются |
| `GET` | `/api/me/data` | клиент | Выгрузка своих данных (право на доступ, 152-ФЗ ст. 14) |
| `GET` | `/api/tables` | все | Занятость столиков: терраса и зал |
| `POST` | `/api/orders` | клиент или гость | Оформление заказа. Сумму считает сервер, значение из запроса игнорируется |
| `GET` | `/api/orders` | клиент | Свои заказы, включая принятые персоналом по звонку на тот же номер |
| `GET` | `/api/orders/:no` | клиент | Один свой заказ (чужой — `404`) |
| `POST` | `/api/orders/:no/cancel` | клиент | Отмена, пока заказ не встал на плиту |
| `POST` | `/api/staff/login` | сотрудник | Вход по логину и PIN, токен на `STAFF_TOKEN_HOURS` |
| `GET` | `/api/staff/orders` | сотрудник | Очередь кухни: незакрытые и недавно выданные заказы, с телефонами |
| `POST` | `/api/staff/orders` | сотрудник | Заказ, принятый по телефонному звонку |
| `POST` | `/api/staff/orders/:no/accept` | сотрудник | Принять заказ и назвать время готовности |
| `POST` | `/api/staff/orders/:no/status` | сотрудник | Сменить статус: `cooking`, `ready`, `done`, `cancelled` |
| `POST` | `/api/staff/orders/:no/eta` | сотрудник | Изменить обещанное время |
| `GET` | `/api/staff/tables` | сотрудник | Карта столиков |
| `POST` | `/api/staff/tables/:n/toggle` | сотрудник | Занять или освободить столик вручную |
| `GET` | `/api/stream?token=…` | клиент и сотрудник | Живые события (SSE): заказ изменился, столики изменились, `ping` |
| `GET` | `/health` | мониторинг | Состояние сервера: время, число подписчиков, режим SMS |

Статусы заказа: `new` → `accepted` → `cooking` → `ready` → `done`; в любой момент до плиты — `cancelled`.

Токен передаётся заголовком `Authorization: Bearer …`. Исключение — поток событий:
`EventSource` не умеет заголовки, поэтому там токен идёт параметром адреса
(в журнал доступа nginx этот адрес не пишется, см. `deploy/nginx.conf`).

Телефон гостя сервер **не отдаёт клиенту** и **не пишет в журнал**: поле `phone`
заполняется только в ответах персоналу.

## Запуск локально

```bash
cd server
npm install
cp .env.example .env
```

В локальном `.env` достаточно поменять две строки:

```
NODE_ENV=development
SMS_PROVIDER=log
CORS_ORIGINS=http://localhost:5173
```

`SMS_PROVIDER=log` ничего не отправляет: код печатается в журнал сервера и возвращается
приложению в поле `devCode`, так что вход проверяется без реальных SMS и без трат.
При `NODE_ENV=development` секрет `JWT_SECRET` можно не задавать — он сгенерируется
случайно (после перезапуска придётся войти заново).

```bash
npm run dev      # сервер на http://localhost:3000, перезапуск при правках
```

Приложение локально ходит на сервер напрямую, без nginx, поэтому адрес API — **без** `/api`:

```powershell
# в корне проекта, PowerShell
$env:VITE_API_URL="http://localhost:3000"; npm run dev
```

Проверка того, что всё связалось (создаёт тестовый заказ, на боевом сервере не запускать):

```bash
cd server
npm run seed:staff -- kitchen 1234 Кухня
npm run test:smoke -- http://localhost:3000 kitchen 1234
```

Проверка типов: `npm run typecheck` (или `npx tsc --noEmit`).

## Развёртывание на сервере

### Что нужно

- Виртуальная машина **в России** (Yandex Cloud, VK Cloud, Selectel, Timeweb) —
  требование 152-ФЗ, ч. 5 ст. 18: база с данными россиян должна находиться в РФ.
  Хватает 2 ГБ памяти и 20 ГБ диска.
- Ubuntu 22.04/24.04, установленные `docker` и плагин `docker compose`.
- Домен, A-запись которого указывает на адрес машины.
- Открытые порты 80 и 443. Порт 3000 наружу **не открывается**: к серверу ходит только nginx.

### Первый запуск

```bash
# на сервере
sudo mkdir -p /opt/graff && cd /opt/graff
git clone <адрес репозитория> .

cp server/.env.example server/.env
nano server/.env        # JWT_SECRET, SMS_*, STAFF_LOGIN/STAFF_PIN, TABLES_*, WORK_*

# домен в конфигурации nginx (три места)
sed -i 's/graff.example.ru/ваш-домен.ру/g' deploy/nginx.conf
mkdir -p deploy/certbot-www
```

Сертификат нужно выпустить **до** первого старта nginx: без файлов сертификата
nginx не поднимется (см. следующий раздел). Дальше:

```bash
docker compose build     # собирает клиента и сервер, компилирует better-sqlite3
docker compose up -d
docker compose ps        # app должен быть healthy
curl -s https://ваш-домен.ру/health
```

Что происходит при сборке: стадия `client` собирает приложение Vite с `VITE_API_URL=/api`,
стадия `deps` ставит рабочие зависимости сервера, стадия `web` кладёт готовую статику
в образ nginx, стадия `app` собирает образ сервера. Подробности — в комментариях `Dockerfile`.

### Обновление версии

```bash
cd /opt/graff
git pull
docker compose build
docker compose up -d
```

База лежит в томе `graff-data` и пересборку переживает. Перед обновлением — резервная копия.

### Журналы и остановка

```bash
docker compose logs -f app      # журнал сервера (телефонов и кодов в нём нет)
docker compose logs -f nginx
docker compose restart app
docker compose down             # остановить всё; том с базой остаётся
```

## Сертификат Let's Encrypt (certbot)

certbot ставится на хост, сертификаты лежат в `/etc/letsencrypt` и монтируются
в контейнер nginx только для чтения.

```bash
sudo apt update && sudo apt install -y certbot

# первый выпуск: nginx ещё не работает, порт 80 свободен
sudo certbot certonly --standalone -d ваш-домен.ру \
  -m почта@кафе.ру --agree-tos --no-eff-email

sudo docker compose -f /opt/graff/docker-compose.yml up -d
```

Продление раз в 90 дней. nginx уже занимает порт 80, поэтому продлеваем способом
`webroot` — каталог `deploy/certbot-www` смонтирован в контейнер, а запросы
`/.well-known/acme-challenge/` отдаёт блок на 80-м порту:

```bash
sudo certbot certonly --webroot -w /opt/graff/deploy/certbot-www -d ваш-домен.ру
```

Чтобы продление шло само и nginx подхватывал новый сертификат, один раз пропишем хук:

```bash
sudo mkdir -p /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/graff-nginx.sh >/dev/null <<'EOF'
#!/bin/sh
docker compose -f /opt/graff/docker-compose.yml exec -T nginx nginx -s reload
EOF
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/graff-nginx.sh

sudo systemctl status certbot.timer   # таймер продления ставится вместе с certbot
sudo certbot renew --dry-run          # проверка, что всё сработает
```

## Сотрудники кухни

Первый сотрудник создаётся автоматически при первом старте из переменных
`STAFF_LOGIN`, `STAFF_PIN`, `STAFF_NAME`. После этого переменные можно убрать из `.env`.

Остальных заводим командой:

```bash
docker compose exec app npm run seed:staff -- <логин> <PIN> <имя> [staff|admin]
# пример
docker compose exec app npm run seed:staff -- aslan 4821 Аслан staff
```

Логин — от 2 до 32 символов, PIN — только цифры, не короче 4. PIN хранится в базе
как scrypt-хэш и восстановлению не подлежит: забытый PIN меняется новой записью.
Токен сотрудника живёт `STAFF_TOKEN_HOURS` часов (по умолчанию 12) — смена кончилась,
вход на кухне нужен заново.

У каждого повара должен быть **свой** логин: журнал `audit` пишет, кто менял статус заказа.

## SMS: sms.ru или smsc.ru

Оба оператора работают одинаково: регистрируем кабинет на юридическое лицо
(ИП или ООО, на которое оформлено кафе), пополняем баланс, получаем ключ.

**sms.ru** — в `.env`:

```
SMS_PROVIDER=smsru
SMS_API_ID=ключ из кабинета (Настройки → API)
SMS_SENDER=GRAFF
```

**smsc.ru** — в `.env`:

```
SMS_PROVIDER=smsc
SMS_LOGIN=логин
SMS_PASSWORD=пароль
SMS_SENDER=GRAFF
```

Про имя отправителя (важно): **буквенное имя отправителя нужно регистрировать заранее**.
Заявка подаётся в кабинете оператора, к ней прикладывают документы на компанию и
подтверждение прав на название (свидетельство на товарный знак, договор, вывеска).
Согласование занимает от одного до нескольких рабочих дней, у сотовых операторов
дополнительно берётся ежемесячная плата за имя. **Незарегистрированное имя означает,
что SMS просто не доставляются** — код входа не придёт, и в журнале будет отказ оператора.
Пока имя не согласовано, можно временно работать с общим именем оператора.

Текст сообщения задаётся в `SMS_TEMPLATE`, `{code}` заменяется на код. Код входа —
сервисное сообщение, отдельного согласия на рекламу для него не нужно, но и рекламы
в нём быть не должно: за это штрафует ФАС.

Расход можно оценить заранее: одно SMS на вход, повторная отправка — не чаще раза
в минуту, не больше `CODE_PER_HOUR` на номер в час. Эти пределы защищают и от накрутки трат.

## База данных и резервные копии

База — один файл SQLite. В контейнере это `/app/server/data/graff.db`, снаружи —
именованный том Docker:

```bash
docker volume ls | grep graff-data          # обычно graff_graff-data
docker volume inspect graff_graff-data      # путь на диске: /var/lib/docker/volumes/…/_data
```

Рядом с базой лежат файлы `graff.db-wal` и `graff.db-shm` (журнал WAL). **Копировать
только `graff.db` у работающего сервера нельзя** — копия будет неполной. Есть два
правильных способа.

**Способ 1: с короткой остановкой (30 секунд, самый надёжный).**

```bash
cd /opt/graff
sudo mkdir -p /var/backups/graff
docker compose stop app
docker run --rm -v graff_graff-data:/data -v /var/backups/graff:/backup alpine \
  sh -c "cp /data/graff.db /backup/graff-$(date +%F).db"
docker compose start app
```

**Способ 2: без остановки, средствами SQLite (`.backup`).** Если на хосте есть `sqlite3`:

```bash
sudo apt install -y sqlite3
DB=/var/lib/docker/volumes/graff_graff-data/_data/graff.db
sudo sqlite3 "$DB" ".backup '/var/backups/graff/graff-$(date +%F).db'"
```

`.backup` делает согласованную копию прямо на работающей базе: WAL при этом
учитывается, отдельные файлы `-wal` и `-shm` копировать не нужно.

Ежедневная копия по расписанию (`sudo crontab -e`):

```
15 4 * * * /usr/bin/sqlite3 /var/lib/docker/volumes/graff_graff-data/_data/graff.db ".backup '/var/backups/graff/graff-$(date +\%F).db'" && find /var/backups/graff -name 'graff-*.db' -mtime +30 -delete
```

**Восстановление:**

```bash
docker compose stop app
docker run --rm -v graff_graff-data:/data -v /var/backups/graff:/backup alpine \
  sh -c "rm -f /data/graff.db-wal /data/graff.db-shm && cp /backup/graff-2026-09-01.db /data/graff.db"
docker compose start app
```

Резервные копии содержат те же персональные данные, что и база: их нельзя вывозить
за пределы России и нельзя складывать в общедоступное хранилище. Держите их на том же
сервере (или в российском объектном хранилище) с ограниченным доступом и своим сроком
хранения — 30 дней достаточно.

## Соблюдение 152-ФЗ

Что уже сделано в коде и в этой схеме развёртывания:

- **База в России.** Данные лежат в SQLite на диске виртуальной машины российского
  провайдера (152-ФЗ, ч. 5 ст. 18). Никакие персональные данные не уходят в зарубежные
  сервисы; единственный внешний вызов — российскому оператору SMS.
- **Согласие до обработки.** `POST /api/auth/request-code` без `consent: true` отказывает,
  и это же проверяется при гостевом заказе. Версия документов, под которой дано согласие,
  сохраняется рядом с записью гостя.
- **Журнал `audit`.** Каждое согласие, отзыв рекламного согласия, удаление аккаунта и
  действия персонала с заказами записываются в таблицу `audit` с меткой времени и
  исполнителем. Это доказательство согласия (доказывать обязано кафе) и материал для
  расследования инцидента.
- **Права гостя.** Доступ к своим данным — `GET /api/me/data`, уточнение — `PATCH /api/me`,
  удаление вместе с отзывом согласия — `DELETE /api/me`. При удалении гость стирается,
  а его заказы обезличиваются: кафе сохраняет учёт, но связь с человеком теряется.
- **Сроки хранения.** `ORDER_KEEP_DAYS` (по умолчанию 365 дней) — заказы старше срока
  удаляются автоматически, уборка запускается каждые 6 часов. Коды из SMS живут
  `CODE_TTL_MINUTES`, история запросов кодов — 7 дней. Хранить «бессрочно» нельзя.
- **Минимум данных.** Собираем только телефон и имя — без них заказ не отдать.
  Телефон не попадает ни в журналы (`LOG_BODIES=0`), ни в ответы клиенту.
- **Защита.** Канал закрыт TLS, порт сервера наружу не опубликован, PIN и коды хранятся
  только в виде хэшей, частота запросов ограничена.

Что нужно сделать людям, а не коду:

1. **Уведомить Роскомнадзор о намерении обрабатывать персональные данные** —
   **до** начала обработки, то есть до запуска приложения (152-ФЗ, ст. 22).
   Уведомление подаётся через портал `pd.rkn.gov.ru`, освобождений для кафе нет.
   При изменении сведений (адрес, цели, состав данных) подаётся уведомление об изменениях.
2. **Опубликовать Политику обработки персональных данных** и держать её доступной
   из приложения; сроки хранения в политике должны совпадать с настройками сервера.
3. **Назначить ответственного за организацию обработки** персональных данных и
   контактное лицо на случай инцидента.
4. **Утечка: 24 часа на первичное уведомление** Роскомнадзора о факте инцидента
   (через форму `pd.rkn.gov.ru/incidents/`: предполагаемые причины, предполагаемый вред,
   принятые меры, контакт) и **72 часа на результаты внутреннего расследования** —
   кто и какими действиями к нему привёл. Именно для этого нужны журнал `audit`
   и журналы контейнеров: держите их доступными, а срок хранения — не меньше месяца.
5. **Ограничить доступ к серверу.** Доступ по SSH только по ключу, отдельные учётные
   записи, список тех, кто имеет доступ к базе. Резервные копии — там же, в России.

Подробный разбор требований с нормами — в `docs/legal-requirements.md`.

## Если что-то не работает

| Симптом | Куда смотреть |
| --- | --- |
| `app` не стартует, в журнале `JWT_SECRET не задан` | не заполнен `JWT_SECRET` в `server/.env` |
| nginx падает при старте | сертификат ещё не выпущен или домен в `deploy/nginx.conf` не заменён |
| Код из SMS не приходит | `docker compose logs app` — там причина отказа оператора; проверьте баланс и регистрацию `SMS_SENDER` |
| Приложение открывается, но заказы не отправляются | приложение собрано без `VITE_API_URL`; пересоберите: `docker compose build --no-cache` |
| Статусы не обновляются вживую | проверьте, что запрос `/api/stream` не буферизуется прокси (секция SSE в `deploy/nginx.conf`) |
| `better-sqlite3` не собирается | в стадии `deps` образа должны стоять `python3 make g++` — они есть в `Dockerfile` |
